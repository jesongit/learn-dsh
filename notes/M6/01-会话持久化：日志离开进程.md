# M6 · 第 1 节 · 会话持久化：日志离开进程

> 备课出处（选读）：[deepseek-harness/docs/subsystems/session.zh.md](../../deepseek-harness/docs/subsystems/session.zh.md)（13 种核心事件变体与投影规则）、[docs/subsystems/persistence.zh.md](../../deepseek-harness/docs/subsystems/persistence.zh.md)（JSONL provider、`session/flush` 检查点、崩溃恢复、SessionHeader）。

## 本节目标

让事件日志**活过进程的生命周期**：落盘（JSONL）、重启恢复、恢复后一切投影照常工作。AGENTS.md 的亲手点在这兑现：亲手重启进程，继续上次对话。

## 1. 一句话理解

**持久化的对象只有一份：事件日志**——因为它是唯一事实来源，模型历史、UI、账本、压缩哨兵全部能从它重建。保存 = 把日志逐行写出；恢复 = 把日志逐行读回；之后整个系统自然「想起」一切——**投影不需要知道进程死过**。

## 2. 概念讲解

### 为什么是 JSONL：格式与纪律同构

日志是 append-only 的，落盘格式选 **JSON Lines**（一行一个 JSON 对象）——文件的写入方式（只追加）与日志的写入方式（只追加）同构。崩溃时最多丢最后没写完的一行，前面的行永远完好。对照 harness：JSONL provider、`session/flush` 检查点、崩溃恢复，同一条思路的工业版。

### 序列化边界是双向的：出容易，进才是主菜

- **出（保存）**：`dataclasses.asdict` 递归转纯 JSON（M3-01 老朋友）——vocab 的 ● 标记字段（dataclass）全部被它转净；编码用 `ensure_ascii=True` 或显式 `encoding="utf-8"`——M4-01 疑点 Q7 的预言兑现：**文件正是「编码未知的消费者」**。
- **进（恢复）**：真正的难点。读回的 `data["usage"]` 是 dict，而投影代码访问的是 `usage.input_tokens` **属性**（M4-01 TODO(N) 的教训「不是 dict 是 dataclass」）——所以恢复时必须**按类型重建**：content 块按 `block["type"]` 分派回 `TextBlock/ToolCallBlock/ToolResultBlock`，usage 重建 `TokenUsage`。**只存不加，读回来就跑不起来**——这就是词汇表要「登记处」的另一半理由：它同时是序列化/反序列化的字段清单。

## 3. 关键代码片段讲解

恢复方向的类型重建——投影期待 dataclass 属性，所以按 type 分派重建（伪代码形状）：

```python
def _revive_block(b: dict) -> ContentBlock:
    if b["type"] == "text":
        return TextBlock(text=b["text"])
    if b["type"] == "tool-call":
        return ToolCallBlock(id=b["id"], name=b["name"], arguments=b["arguments"])
    if b["type"] == "tool-result":
        return ToolResultBlock(tool_call_id=b["tool_call_id"],
                               content=[_revive_block(x) for x in b["content"]],
                               is_error=b["is_error"])
```

读法：`tool-result` 的 `content` 是块列表——**递归重建**，和 M3-01 讨论 `asdict` 递归时是同一棵树，只是方向相反。

### 编码实录

本节的 bug 谱系有一半是**老师的 spec 写出来的**，另一半是词汇表漂移——双向扫描在收官节再次成立：

1. **`event.asdict()`**——asdict 是模块**函数**不是方法，三条测试同炸；
2. **content 清单错位**——混入 harness 的 `system/message`（PAgent 从不落它）、漏掉 tool/result/steering/context 三类；
3. **`_revive_chunk` 字段漂移三连**——ToolCallDelta 缺 `index`、`arguments_delta` 写成 `args`；UsageChunk / Finish 凭空多出 `index`（它们只有单字段）；
4. **`ToolCallBlock` 的 `args`/`arguments`**——同样漂移；
5. **KeyError: 'type'（最深的一条，spec 自相矛盾）**——save 的 spec 用裸 `asdict`（**ClassVar 不进 asdict**，块落盘后没有 type 标签），revive 的 spec 却按 `b["type"]` 分派——两个 spec 单看都对、合在一起必炸，用户忠实实现两边，KeyError 替 spec 顶了罪。修法：save 侧 `_dump_block` 补标签（M3-01 疑点 Q3 的 `{"type": b.type, **asdict(b)}` 首次生产服役）；
6. **双层信封（老师的伪代码笔误）**——`data = asdict(event)` 取的是**整个信封**，再套进 `"data"` 键变双层嵌套；修正为 `asdict(event)["data"]`。连带发现 `asdict(BlockEnd)` 会剥掉**内嵌块**的标签——`_dump_chunk` 特判补回。

修复后的验证仪式：落盘文件里 BlockEnd 行内嵌块带 `"type": "tool-call"` ✓、恢复后投影与账本和原始逐条相等 ✓。

<a id="qa-persist"></a>
### 对话疑点

**Q15 有没有更好的序列化方案？** 四方案对照（恢复自动化 / 追加崩溃安全 / 人可读 / 跨语言）：**pickle** 恢复零工作但对日志全面倒退（非追加、二进制、load 执行任意代码、跨语言死）；**pydantic 判别联合 + TypeAdapter** 技术全面占优——原生内置你手写的分派表——但要求词汇表 pydantic 化（ClassVar 判别字段要翻成真字段，即重开 M3-01 的决策）或维护两份类型定义（两份真相病）；**SQLite** 是日志变大后的正解。harness 生产系统选的也是 JSONL。结论：v0 手写 revive 是学习顺序（手搓一遍 mini-TypeAdapter 才知道它省了什么），「持久化层判别联合化」列入 PAgent 2.0。

**Q16 序列化边界是双向的，两半纪律不同。** 出（保存）：asdict 会剥 ClassVar——**类型标签必须在写侧补回**（`_dump_block`/`_dump_chunk`），否则恢复无从分派；进（恢复）：按词汇表重建，● 字段全走 dataclass。反过来如果选「读侧猜类型」（按特征键），省了写侧标签、换来键位重叠的脆弱——事件溯源的标准姿势是**标签写在写侧**。

**Q17 文件编码这次为什么用显式 utf-8 而不是 ensure_ascii=True？** M4-01 Q7 说「编码未知的消费者用 True」；这里消费者是我们自己的 load（显式声明 `encoding="utf-8"`），编码已知且受控——直接 utf-8 存原文，文件可读且不膨胀。规则复述：True 给未知，显式给已知。

## 7. TS vs Python 差异与坑

- 反序列化回 dataclass 需要**类型信息**——TS 侧同样要手写 reviver（JSON.parse 不认类型）；两边对称。Pydantic 的 `TypeAdapter` 能按注解自动重建，v0 不引，手写一遍才懂它省了什么。
- 坑预告：● 字段（dataclass）之外，`time` 是毫秒 int、`content` 是列表——恢复函数要覆盖词汇表**每一行**，漏一行就是恢复后某次投影炸 AttributeError。
